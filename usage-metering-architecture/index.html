    Usage Metering Architecture

    Phase 3 complete — PRs #308–#317 · June 2026

    Overview

    Mental Model

    AdPros separates two kinds of limits. Usage meters track billable AI actions per billing period. Brand capacity limits how many competitor brands a user may track.

    KindWhat it limitsStored onResets
    Usage metersBillable AI actions per billing periodusers.chats_*, report_credits_*, alert_runs_*Plan change, Stripe renewal, admin set_plan, plan_upgrade coupon
    Brand capacityHow many competitor brands a user may trackDerived from plans + users.brands_bonus; enforced by counting brands rowsPlan change, brand_add coupon, admin edits to brands_bonus
    Note: Seats are display-only until an invite flow exists. The legacy single pool (users.credits_remaining / credits_total) is no longer consumed or written by billing sync.
    Core Concepts

    The Three Usage Meters

    💬
    Chat
    chats_remaining / chats_total
    Agent questions

    Single-brand and comparison. User label: Chats.

    📄
    Report
    report_credits_remaining / report_credits_total
    PDF / document exports

    User label: Report credits.

    ⚡
    Alert
    alert_runs_remaining / alert_runs_total
    Scheduled workflows

    User label: Alert runs.

    Each meter has a remaining balance and a total cap. Audit rows go to credit_transactions with negative amount on deduct, positive on grants.

    Capacity

    Brand Limits

    Brand limits are not deducted from usage meters. Adding a brand is free — BRAND_INGESTION maps to no meter.

    Effective limit calculation

    effectiveBrandLimit = planEntitlements.brandsLimit + (user.brands_bonus || 0)

    brandsLimit resolution via resolveBrandsLimitFromRow:

    1. If brands_fair_use → 999,999
    2. Else if brands_tracked is set → that value
    3. Else → legacy brands_limit column

    Where enforcement runs

    Entry pointHelper
    POST /api/brands/ingestInline count vs limit
    POST /api/brandscheckUserBrandPlanLimit()
    Brand onboarding toolslib/brands/onboarding-policy.ts
    Client pre-check (Add Brand page)Hardcoded BRAND_LIMITS map — server is source of truth

    Count query: active brands where brands.added_by = userId and archived_at IS NULL. On limit exceeded: 403 with plan name and limit.

    Runtime

    Consumption Flow

    High-level path for any billable action

    1

    User action triggers checkUsage / checkUsageForCreditAction

    2

    If allowed → execute feature. If denied → 403 + meter-specific error code

    3

    After success: deductUsage / deductUsageForCreditAction

    4

    deduct_usage_meter RPC updates users.*_remaining and inserts into credit_transactions

    Stripe Integration

    Billing Sync

    Central orchestrator: applyPlanBillingState in lib/usage/sync-user-billing-state.ts. Never writes credits_remaining. Calls syncUserUsageMetersFromEntitlements → reset_usage_meters RPC.

    full_reset

    Checkout, renewal, upgrade, admin set_plan, plan_upgrade coupon. Sets remaining = total = plan caps.

    cap_downgrade

    Downgrade / cancel to FREE. Total = new plan caps; remaining = min(current, new cap).

    Walkthrough

    End-to-End Examples

    A — User sends a chat

    1

    Client → POST /api/chat

    2

    Resolve scope → CHAT_SINGLE_BRAND or CHAT_COMPARISON

    3

    checkUsageForCreditAction → loads chats_remaining, applies fair-use

    4

    If denied → 403 insufficient_chats. If allowed → LLM stream

    5

    On success → chats_remaining −1 + audit row

    B — User adds a brand

    1

    Client → POST /api/brands

    2

    checkUserBrandPlanLimit counts brands vs limit

    3

    If at cap → 403. If allowed → brand upsert; no meter deduction

    C — Stripe renewal

    1

    Webhook invoice.paid

    2

    Resolve plan → getPlanEntitlements

    3

    applyPlanBillingState full_reset → all meters reset to plan totals

    D — Daily competitor workflow

    1

    Cron picks due workflow; template usage_meter = 'alert'

    2

    checkWorkflowExecutionUsage → checkUsage(userId, "alert", 1)

    3

    On success → deductWorkflowExecutionUsage → alert meter −1

    Ops

    Operational Checklist

    Before changing limits or billing behavior:

    1

    Edit the assignable plan row in Admin → Plans (not only the marketing GROWTH row).

    2

    Confirm Stripe price → assignable plan mapping matches.

    3

    For new workflow templates, set workflow_templates.usage_meter to report or alert.

    4

    Apply migrations in order: 104 → 105 → 106 → 107.

    5

    Verify admin Users columns and Settings bars after plan or grant changes.
