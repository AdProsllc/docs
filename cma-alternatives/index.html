Alternatives to Claude Managed Agents

Infrastructure decision brief · v1

01 · Executive Summary

How to choose

Claude Managed Agents (CMA) is a hosted agent harness — sandboxing, sessions, memory, tool execution, and tracing, all run by Anthropic for $0.08/session-hour plus tokens. The alternatives split along two axes: who runs the infrastructure, and which models you can use. The right choice depends on lock-in tolerance, scale, and how much of the moat lives inside the agent's memory.

The decision in one sentence If your moat is memory and learning loops, own the harness. If your moat is the agent's task quality and you want to ship fast, let Anthropic run it.

The four buckets

A

Hosted, Claude-native

CMA. Fastest to ship, deepest Claude tuning, highest lock-in. Best when speed beats flexibility and Claude is already the default.

B

Hosted, model-agnostic

Bedrock AgentCore, Deep Agents Deploy, DigitalOcean Gradient. Someone else runs the infra, models stay swappable.

C

SDK / library, you deploy

Claude Agent SDK, LangGraph, CrewAI. Full control over deployment. Engineering cost but no per-session platform fee.

D

Self-hosted OSS

OpenClaw, Multica, Cabinet, Eigent. Maximum control, zero lock-in, full ops cost on your team.

Three things people miss

i. Memory = lock-in

Models are easy to swap. Once agents have written months of memory into a proprietary store, switching costs explode.

ii. $0.08/hr scales

One agent for an hour is a rounding error. 500 agents running concurrently is $40/hr just for the harness, on top of tokens.

iii. Infra is solved

The hard part isn't the harness — it's wiring agents into real data sources cleanly. That work is the same on every platform.

02 · Recommendations for Ad Pros

Mapped to what you're actually building

Based on the current Ad Pros AI stack — Noor (ClickUp + BigQuery + Supabase + Claude API), the 8-agent Workflow Factory, the Media Intelligence Pipeline processing ~5K Meta ads/day, and the AI twin video pipeline — here's how the alternatives map to specific projects.

RECOMMENDED PRIMARY · NOOR / WORKFLOW FACTORY

Claude Agent SDK + your existing stack

Noor is already built on ClickUp, BigQuery, Supabase, and the Claude API. The Agent SDK formalizes what you have — agent loop, tool execution, context compaction — without forcing you onto Anthropic's hosted runtime. Keep Supabase as the memory store, BigQuery as the data layer, and skip session-hour fees on agents that run constantly.

Why

Your moat is the data layer + workflow logic, not the harness

Cost vs CMA

Save ~$60/mo per agent running 24/7 ($0.08 × 730 hr)

Risk

You own ops, but you're already running prod infra

USE FOR · MEDIA INTELLIGENCE PIPELINE

Stay on Anthropic Batch API

Don't move the ~5K ads/day pipeline to CMA. Batch API is 50% cheaper for high-volume async work, and you're not running a long-horizon agent — it's a stateless classification pipeline at scale. CMA's value is sessions and memory; you don't need either here.

Use CMA only for: the QA audit agent that reasons across full classification output.

WORTH PILOTING · CLIENT-FACING (FUTURE)

Claude Managed Agents

If Noor ever gets productized for clients (white-label agent infra for DTC brands), CMA's sandboxing, scoped permissions, and identity isolation are exactly what would otherwise take 3 months to build. Single-tenant per-client agents with session-hour pricing maps cleanly to client billing.

Why: multi-tenant security is the hardest part to build correctly.

WATCH, DON'T ADOPT · MULTI-MODEL

Deep Agents Deploy (LangChain)

Useful insurance against Anthropic pricing or capability shifts, but not needed today — Claude is the default and it's working. Re-evaluate if a specific agent ever benefits from Gemini's long context or a local model for cost/privacy.

Trigger to revisit: Claude pricing increase, or vertical where Gemini's context window matters.

SKIP · NOT YOUR STACK

Bedrock AgentCore

Only makes sense if you were already on AWS. Adds vCPU-hour + GB-hour pricing complexity, AWS IAM overhead, and a second cloud to manage. You're on Supabase + Cloudflare R2 — staying there is correct.

SKIP · TEAM SIZE

Self-hosted OpenClaw / Multica

Right answer for a 200-person org with a platform team. At ~26 people with most engineering effort going into the products themselves, the ops burden of self-hosting an agent runtime is a tax you don't need to pay yet.

SUMMARY

Three patterns, not eight

Document the harness boundary clearly: which agents call CMA, which call the Agent SDK directly, which use Batch API. Three patterns is fine; eight is chaos.

SUGGESTED NEXT 30 DAYS
  1. 01. Audit current Noor agents → which actually need long-running sessions vs. one-shot calls? Most don't.
  2. 02. Pick one agent to pilot on CMA. The QA audit pipeline or a competitive intel deep-research agent are good candidates.
  3. 03. Keep Supabase as the source-of-truth memory store regardless of harness. Don't let agent memory get trapped in any vendor.
  4. 04. Document the harness boundary so the team knows when to reach for CMA vs. SDK vs. Batch API.

04 · Decision Questions

Questions to ask before choosing

Work through these in order. The first three eliminate most options; the rest refine the choice.

01

Does this agent actually need a long-running session?

If the work is one-shot or batch-classifiable, an agent harness isn't needed at all — use Messages API or Batch API. CMA shines for tasks that run minutes to hours with stateful memory.

02

Where does the agent's memory live, and who owns it?

This is the lock-in question. If memory is the moat (agents accumulating client-specific context over months), keep memory in your own database (Supabase) regardless of harness. If memory is ephemeral, vendor-managed is fine.

03

How many agents will run concurrently at peak?

1–10: hosted is fine. 50+: model the session-hour cost carefully — at $0.08/hr × 50 agents × 730 hr/mo = $2,920/mo just for the harness, before tokens. At that point self-deployed Agent SDK pays for itself.

04

Do you need multi-model flexibility now or in the future?

If committed to Claude (you are), CMA is fine. If a specific agent benefits from Gemini's long context, GPT-5's reasoning, or a local model for privacy, choose model-agnostic upfront — retrofitting is painful.

05

Who handles security, identity, and tenant isolation?

Internal agents: anything works. Client-facing or multi-tenant: hosted platforms (CMA, AgentCore) save 2–3 months of security work. This is where managed pricing usually pays off.

06

What's the team's ops capacity?

Self-hosting OpenClaw means someone owns Kubernetes, sandbox security, observability, on-call. Without a platform engineer dedicated to this, hosted wins by default.

07

How fast does this need to ship?

CMA: days to prototype, days to production. Agent SDK: weeks. Self-hosted OSS: months. The fastest path to 'agent in production' is almost always hosted.

08

What's the data residency / compliance requirement?

If client contracts require data stays in specific regions or never touches Anthropic servers, only self-hosted works. For most DTC ecommerce work this isn't a constraint.

09

What does failure look like, and who handles it at 2am?

Hosted: Anthropic's on-call handles infra, you handle prompt/logic. Self-hosted: it's all you. Factor incident response cost into the comparison.

10

How will agent quality get measured, and does the platform help?

CMA Console gives tracing for free. LangSmith does this on top of LangGraph. Self-hosted means building evals and observability yourself. Eval velocity is often the real bottleneck.

11

What's the migration path if you're wrong?

See the Migration Risk tab. Bias toward decisions that are reversible in weeks, not quarters.

12

Are you optimizing the right thing?

Most teams overweight infrastructure choice and underweight prompt quality, tool design, and data plumbing. The harness rarely determines whether the agent works.

Why model-agnostic harnesses matter as insurance.
REVERSIBILITY PRINCIPLES
  1. Keep memory in your own database (Supabase) regardless of harness — never in vendor stores
  2. Wrap MCP tool calls in your own interface so swapping harness doesn't touch tool code
  3. Standardize agent definitions in markdown/YAML you control, not vendor APIs
  4. Run evals against agent outputs, not harness internals — outputs port across platforms
  5. Pilot any new harness on one non-critical agent for 30 days before broader adoption
THE CHEAP INSURANCE

Even if committed to CMA today, do these three things to keep the door open:

  • Mirror agent memory writes to Supabase as the source of truth
  • Define agents in your own markdown/JSON spec, then translate to CMA API on deploy
  • Keep a working Claude Agent SDK fallback for at least one critical agent

~1 week of upfront work. Saves 6-10 weeks if you ever need to switch.
